# 开发流水线

一条从需求到交付的流水线。**需求讨论是唯一需要人参与的环节**；规格落盘之后，直到最终报告，不再索要用户输入。

## 工具名不会告诉你该用哪个

本插件挂出的所有角色工具，在你的工具清单里**描述完全相同** —— 上游的委派工具不支持按角色定制描述。因此本文档逐处点名工具，照着调用，不要凭描述猜。

**命名规则**：单模型角色是 `subagent_<role>`，只有配了多个模型的角色才带 `_<alias>` 后缀，同一个角色不会两种形态混用。默认配置下每个角色只有一个模型，所以通常挂出的是不带后缀的 `subagent_implementer`、`subagent_reviewer`、`subagent_researcher`。

看你自己的工具清单确认当前实际挂了哪些——`list_agents` 列的是已经存在的子代理会话，不是可调用的工具，这里用不上它：

- `subagent_implementer`（或按上面的规则带后缀） —— 实现任务
- `subagent_reviewer` / `subagent_reviewer_<alias>`（可能有多个实例，每个绑不同模型） —— 评审
- `subagent_researcher`（或按上面的规则带后缀） —— 调研，**默认流程不调用它**

## 并发限制

**同一个仓库不支持同时跑两轮流水线。** 两轮各自记录的 `BASE` 互不可见，产物文件名可能冲突，第 7 步的评审范围会互相污染。当前没有互斥机制，由使用者自行避免同时启动第二轮；发现工作区状态看起来不像自己这一轮留下的（例如预检门第 2 项发现的改动解释不通），按预检门规则处理，不要假设那一定是自己之前的残留。

## 八步

| # | 步骤 | 怎么做 |
|---|---|---|
| 1 | 需求讨论 | 调用 `skill` 工具、`name` 传 `crew-brainstorm`，按其内容执行，落盘规格 |
| 2 | 预检门 | 见下。任一项不满足即中止 |
| 3 | 规格评审 | 调用 `skill` 工具、`name` 传 `crew-converge`，评审对象是规格文件路径；每轮意见落盘到 reviews 目录 |
| 4 | 写实施计划 | 调用 `skill` 工具、`name` 传 `crew-plan`，按其内容执行，落盘计划 |
| 5 | 计划评审 | 同第 3 步，评审对象是计划文件路径 |
| 6 | 逐任务实现 | 见下 |
| 7 | 代码评审 | 同第 3 步，评审对象是 `<BASE>..HEAD` |
| 8 | 最终报告 | 见下，落盘到 reports 目录（引用 reviews 文件，不重抄意见全文） |

**第 1 步之后告诉用户一句**：规格已落盘、进入全自动阶段、完成或中止时汇报，然后直接进入第 2 步。此后到第 8 步之间不要提问。

`crew-brainstorm` 单独被调用时，结尾会让你把规格交给人 review 之后停下——那是它独立使用时的收尾动作。在这条流水线内，上面这句通告就是规格落盘后的交回动作，读到 `crew-brainstorm` 里"不要自己接着往下做"不适用于流水线内的调用，不要因此在这里等待人工确认。

## 第 2 步：预检门

逐项检查，**任一项不满足即中止并报告**，不降级、不绕过、不"先跑起来再说"：

1. **角色路由健康** —— 你的工具清单里必须有 `subagent_implementer` 和至少一个 `subagent_reviewer` / `subagent_reviewer_<alias>`；一个都没有就中止。把你实际看到的 reviewer 工具名逐个写进上面的通告里。

   **挂出几个就是几个视角，不要自己造。** 部署方通过给 reviewer 角色配几个模型来决定视角数量，每个模型挂出一个工具。用两段不同的 prompt 把**同一个**工具派两次不会产生独立视角——那是同一个 provider 与 model，只是让这一环节的成本翻倍。插件的 guard 会拒绝重复派发。
2. **git 工作区干净** —— `git status --porcelain` 输出为空。未跟踪文件和已暂存改动都算脏：第 7 步以 `<BASE>..HEAD` 为评审范围，任何预先存在的改动都会混进来，让"这次做了什么"不可辨认。
3. **产物目录可写** —— 调用 `crew_init`。它的返回值只用来确认目录**已就绪**（本次创建成功，或已经存在），不要用它反推哪个目录是 specs、哪个是 plans、哪个是 reviews、哪个是 reports：`created`/`skipped` 两个数组各自只保留组内相对顺序，一旦创建与已存在的情况混在一起，同一份返回值能对应好几种真实排列，光看这两个数组消不了歧。落盘时具体写到哪个路径，从第 1 步「开始之前」本该做的项目结构探索里观察得到，拿不准就在通告里向用户确认一次。如果 `crew_init` 报告的路径和你观察到的目录对不上、或者判断不出该往哪个目录写，**停下来问用户**，不要猜——规格写进错误的目录，后面每一步都会被这个错误带偏，而且不会有任何报错提示你猜错了。

中止时说清楚：缺什么、怎么修、修好后从第几步继续。

## 第 6 步：逐任务实现

开始前运行 `git rev-parse HEAD` 拿到当前 commit 的 sha，把这个值记在你自己的上下文里——bash 调用之间不保留状态，命令本身不会替你存住它。第 7 步和最终报告都要用到这个值。

按计划逐个任务派 `subagent_implementer`。给它的 prompt 里**必须包含计划文件的路径** —— 纪律 guard 会检查这一点，没有路径的调用会被拒绝。

**不要把计划全文贴进 prompt。** 传路径，让子代理自己读。全文会吃掉你的上下文，而你还要跑完剩下的步骤。

给每个 implementer 的 prompt 应包含：任务编号、计划文件路径、这个任务依赖的前序任务产出了什么接口、以及"实现完自己提交，不要 amend 或 rebase 已有提交"。

一次派一个，不要并行 —— 并行 implementer 会在同一个工作区互相冲突。

**结果怎么回来**：与 reviewer 完全一样。委派工具立刻返回的是子代理 id，不是结果；implementer 结束时运行时**自动**送来一条结算通知，带着它最后一条消息的全文。完整规则见 `crew-converge` 的「结论怎么回来」与「等不到有效结论」两节——包括六种开场白各自的含义、只有最后一条消息会被带回、以及按 `list_agents` 状态的三种处置。逐任务实现一字不差地适用。

所以**派出一个 implementer 之后就结束这一轮**：写一行交班记录（「已派出 <工具名>（<做什么>），等它回报。本轮到此结束。」）然后什么都不调。那一行就是这一轮的收尾动作，不是"什么都不做"。

如果你收到过 `<goal_round>` 消息，说明有活跃 goal 在每轮唤醒你——**先 `update_goal` pause 再写交班记录**，回报到达后 `resume`。完整做法见 `crew-converge` 的「如果这条流水线跑在 goal 循环里」。等待不是一个动作，而是不做动作——`list_agents` 不能用来等（连续调用会被插件的 guard 拒绝）。`job_output` / `job_list` / `job_kill` 管的是 **shell 后台作业**（例如你自己用 `&` 起的开发服务器），与子代理是两套东西：拿子代理 id 去调它们必然失败，但用它们查自己起的后台进程是正常用法。

**怎么算一个任务做完**：以结算通知里的结论为准——它应说明改了什么、测试是否通过、是否已提交。开场白不是 `finished`（被中断、撞上 token 上限、报错、拒绝），或者结论里没说已提交，判定这个任务失败，进入下面失败语义表对应的分支，不要替它连续重试。

判不准的时候用 `git log --oneline` 看这个任务有没有留下提交——那是比任何措辞都硬的证据。

**不要因为等不到回报就自己实现这个任务。** 那份代码没经过评审，还会污染你的上下文。

## 失败与中断

| 情形 | 怎么办 |
|---|---|
| 预检门任一项不满足 | **中止** |
| 规格/计划评审到上限仍有阻塞 | **带遗留清单继续**，报告里标注 |
| 代码评审到上限仍有阻塞 | **带遗留清单继续**，报告里显著标注 |
| 第 6 步部分任务成功、部分失败 | **继续评审成功的部分**，失败任务进遗留清单 |
| 第 6 步结束时 `<BASE>..HEAD` 为空 | **中止** —— 没有交付物，空 diff 的"评审通过"是假阳性 |
| 第 6 步结束时工作区有未提交改动 | **中止** —— 那些改动真实存在却不在评审范围内 |
| 某个 reviewer 子代理被中断 | **中止** —— 收敛判据是"全部无阻塞"，缺一个无法判定 |
| 测试怎么都跑不过 | 按系统化调试排查；仍无解则**中止**，不伪造通过 |

中止时产物全部保留，报告写清：完成到哪一步、卡在哪、修复命令、恢复后从哪继续。

## 红旗清单

出现这些念头就停下来：

| 念头 | 现实 |
|---|---|
| "这轮评审没大问题，差不多收敛了" | 收敛 = 全部 reviewer 无阻塞项。"差不多"不是判据 |
| "有个 reviewer 没配好，用剩下的评审也一样" | 预检门要求至少一个 reviewer 工具；一个都没有就中止，别用别的角色顶替 |
| "只挂了一个 reviewer，我用不同 prompt 派两次凑个第二视角" | 同一个 provider 与 model 派两次不是两个视角，只是成本翻倍。guard 会拒绝 |
| "我自己也能当一个评审者" | 编排者不能兼任评审。你写的东西你自己看不出问题 |
| "上限到了但只差一点，再来一轮" | 上限是规格。剩余问题走遗留清单 |
| "顺手问一下用户确认" | 规格落盘后零打扰，只在完成或中止时汇报 |
| "计划文件太长，摘要贴进 prompt 更省事" | 传路径。摘要会丢掉实现者需要的精确值 |
| "改完的整份文件 `write` 出去，比逐处 edit 干净" | 输出量等于文件全长。超过模型单次输出上限会被静默截断，那一轮以 max-tokens 结束、不会自动继续，流水线就停住了。先 `cp` 出新版本再逐处 `edit` |
| "这一轮把所有阻塞项一次改完，省几次调用" | 一次响应的输出量是各处替换之和，正是撞上限的路径。一处一次 `edit` |
| "这个任务简单，不用 implementer 我直接改" | 你直接改的代码没经过评审，且会污染你的上下文 |
| "代码评审的阻塞项我自己修，比派 implementer 省事" | 同上，而且第 7 步的修复同样要派。派发时 prompt 要给计划路径（过 guard）+ 评审文件路径（告诉它改什么） |
| "工作区有点脏但不影响，先跑" | 脏工作区会混进第 7 步的评审范围 |
| "报告主要写做完了什么，遗留清单可以省" | 遗留清单和驳回意见是报告最有价值的部分。没有它们，报告只是一份自我表扬 |
| "第 6 步没产生 commit，但改动都在，评审一下吧" | 空 diff 评审通过是最危险的假阳性 |
| "reviewer 说的这条不对，跳过不提" | 驳回可以，但理由必须写进 reviews 目录那一轮的评审意见文件 |
| "researcher 闲着，顺便让它查点资料" | 默认流程不调用它。加进来就是加了一个没有判据的环节 |
| "reviewer 工具调用有返回值了，说明它评审完了 / 没意见" | 返回值只是一条子代理 id 的回执，结论经结算通知另行送达，没到齐之前不能当作"没意见"（见 `crew-converge`） |
| "我在这一轮里多查几次，等子代理跑完" | 回报只能在**新的一轮**到达。同一轮里轮询永远等不到，只是白烧 token |
| "我说了『等待通知』，然后再 `list_agents` 确认一次" | 说要停不等于停。**结束一轮 = 写完交班记录后不调用任何工具**。真实会话里这个循环跑了 1069 次，烧光了用户额度 |
| "调个什么工具占位表示我在等（`bash echo`、空提问……）" | 占位不是等待。三种形态都试过，两种已被 guard 拒绝，空提问那种还会卡死流水线 |
| "每轮都被叫醒说『继续推进』，那我就每轮查一次" | 那是 goal 循环在叫你。派出子代理后先 `update_goal` pause，见 `crew-converge` |
| "用 `job_output` 把子代理的输出取出来" | `job_*` 管的是 shell 后台作业，不是子代理。子代理没有取输出的接口，结论由运行时自动送达。（用 `job_output` 查自己 `&` 起的进程是正常的） |
| "子代理迟迟不回报，我自己把这一步做了" | 先用 `list_agents` 看状态，`running` 就继续等。自己顶替 = 这一环没有独立视角，宁可中止并报告 |
| "用 `run_in_background: false` 让 reviewer 立刻把结果给我，省事" | 前台调用不会留下可复审的子代理 id，之后 `send_message` 复审就发不出去了 |
| "guard 又拒了分派，肯定是路径传错了，再试一次" | plans 目录有 `artifactDirs` 与 `gate.plansDir` 两处独立配置，只改一处会让合法路径反复被拒；检查两处是否一致，不要死磕重试 |
| "返回的路径列表里总有一个是 reports，按顺序猜就行" | `created`/`skipped` 各自只保留组内顺序，创建与已存在混在一起时无法还原哪个是哪个；猜错会把产物写进错目录，而且不会有任何报错 |

## 第 8 步：最终报告

### 写报告之前先跑三条检查

1. **`git status --porcelain`** —— 输出必须为空。不为空说明有改动既没提交也不在评审范围内：**先查清是什么**。是你或 implementer 漏提交的，补一次提交；是构建产物或虚拟环境（`.venv/`、`node_modules/`）被误纳入过版本控制，那本身就是一条应当记入报告的问题。**不要跳过这一步直接写报告**——真实会话里报告写完时工作区还挂着几百条未提交的删除。
2. **`git log --oneline <BASE>..HEAD`** —— 确认交付物真的在提交里，条数与你派出的任务数量大致对得上。
3. **数一遍 reviews 目录** —— 每个评审环节的每一轮都该有文件。规格评审到 r3 就该有 3 份，缺了就说明那几轮的结论没落盘，在报告里如实标注。

三条都过了再写报告。

落盘到 reports 目录，文件名 `YYYY-MM-DD-<topic>-report.md`（日期沿用规格文件那一份）。必须包含：

- **产物路径**：规格与计划的**最终版本**（`_rN`）、代码 diff 概要
- **预检门结果**：逐项
- **三个评审环节**各自的轮次、参与的 reviewer、是否收敛，以及每轮评审意见文件的路径
- **被驳回的评审意见**：报告里给出条数与所在文件路径，理由全文留在 reviews 文件里，不在报告里重抄
- **遗留问题清单**（若有，显著标注）
- **测试证据**：跑了什么命令、输出摘要
- **串行降级次数**（若有）
- **下一步选项**：合并 / 提 PR —— 这是用户重新介入的入口，由他决定

- **收尾三条检查的结果**：工作区是否干净、提交条数、reviews 文件是否齐全

**上面每一项都要出现，没有内容的项写"无"。** 真实会话里一份 196 行的报告只写了一行"评审轮次"，遗留清单、驳回意见、reviews 路径、预检门结果、测试证据全部缺失——那份报告读起来像成功交付，实际上把这一趟里所有值得复核的东西都丢了。

报告写完后，用一段话向用户汇报要点，不要让他自己去文件里找。
