# 评审收敛协议

被 `crew` 在三个评审环节调用：规格评审、计划评审、代码评审。三处共用同一套判据。

## 一轮的执行

**在同一条消息里同时调用全部 reviewer 工具。** 工具名是 `subagent_reviewer`（只有一个模型时）或 `subagent_reviewer_<alias>`（配了多个模型时），同一个角色只会是其中一种。用你自己的工具清单确认当前实际挂了哪些实例——`list_agents` 列的是已经存在的子代理会话，不是可调用的工具，这里用不上它。逐个串行调用不会让结论出错，但会白白拉长墙钟时间。

给每个 reviewer 的 prompt 里必须包含：

- **评审对象的文件路径**（规格/计划评审）或 **git 范围**（代码评审，形如 `<BASE>..HEAD`）。传路径，不传全文。
- 它自己去读的指令。评审者有文件读取工具。
- 判据：什么算阻塞、什么算非阻塞。
- **它该把意见写到哪个文件**——完整路径，一个 reviewer 一个，见下面「评审意见落盘」。

## 等结果

reviewer 工具走后台的 continuable 模式，`run_in_background` 省略时默认就是 `true`：调用立刻返回的是 `started subagent <id>`，**不是报告**。reviewer 的结论不会出现在这次工具调用的结果里。

**不要为了"马上拿到结果"把 `run_in_background` 显式设成 `false`。** 那会切到前台等待路径，前台调用不产生持久的子代理 id——复审要用的 `send_message` 从此没有对象可发。

### 结论怎么回来

reviewer 结束时，**运行时自动**给你送一条消息，其中带着它的结论。你不需要去取，也没有可以取的接口。

主通道是**结算通知**，形如：

```
Background subagent <id> finished and will do no further work unless you send it more.
Its closing message:
<reviewer 最后一条消息的全文>
```

开场白按它怎么结束的分几种说法，**只有 "finished" 表示做完了**：

| 开场白 | 含义 | 怎么办 |
|---|---|---|
| `finished and will do no further work…` | 正常做完 | 用它的结论 |
| `was stopped before it finished.` | 被中断 | 按失败处理，**中止** |
| `ran out of room before it finished.` | 撞上 token 上限 | 结论不完整，**中止** |
| `declined the task.` | 拒绝了任务 | **中止** |
| `failed before it finished.` | 出错 | **中止** |
| `It left no closing message.` | 没有任何输出 | 当作没有结论，**中止** |

**只有它最后一条消息会被带回来。** 中间轮次写的分析留在它自己的 transcript 里，你看不到。这正是意见要落盘成文件的原因：最后一条消息只承载**摘要**（评审文件路径、几条阻塞项、每条一句话），细节在文件里。摘要连阻塞项条数都没有，按下面「等不到有效结论」处理。

另一条通道是 `report` 工具：子代理可以在**任何时刻**主动送内容，形如 `Background subagent <id> reported:`。它不受"只有最后一条"的限制，所以长篇评审可能分几次经这条通道到达。收到 `reported:` 不代表它做完了——**做完的判据只有结算通知**。

两种消息都会**开启你的新一轮**。所以：

**发起全部 reviewer 之后，结束你这一轮。**

### 「结束这一轮」具体怎么做

**写一行交班记录，然后什么都不调。** 格式：

```
已派出 <工具名>（<做什么>），等它回报。本轮到此结束。
```

这一行本身就是你这一轮的收尾动作——**它不是"什么都不做"，它是这一轮唯一剩下的工作**。写完这一行，你的响应自然终止，运行时会在通知到达时开启新的一轮。

### 如果这条流水线跑在 goal 循环里

先判断：你收到过以 `<goal_round>` 开头的消息吗？收到过就说明有一个活跃 goal 在**每轮自动唤醒你**。

那种情况下光结束本轮不够——goal 会立刻把你叫醒，你查一次状态、发现子代理还在跑、再写一次交班记录，如此空转。真实会话里这样连转了 12 轮，每轮都是干净的 `completed`，但一步没进。

**派出子代理之后、写交班记录之前，先暂停 goal**：

1. `get_goal()` 拿到 `goal_id` 与 `revision`（compare-and-set 需要）。
2. `update_goal(goal_id, revision, action: "pause")`。
3. 再写交班记录，结束本轮。

子代理的结算通知是独立机制，**不受 goal 暂停影响**，照样会唤醒你。醒来后先 `update_goal(..., action: "resume")` 再继续流程。

忘了 resume 只会让流水线退化成纯事件驱动（仍能走完）；不 pause 则是每轮烧一次模型请求换一句"还在等"。

**不要自己为这条流水线创建 goal。** 宿主允许模型推断"长期任务意图"并自动 `create_goal`，但 crew 流水线本身就是事件驱动的——子代理回报会自动开启你的新一轮，goal 循环叠加上来只会空转。

**不要为「等待」再找一个动作。** 等待不是你能执行的事，没有任何工具能让通知来得更早。真实会话里编排者试过三种填充动作，全都无效：

| 它试过的 | 结果 |
|---|---|
| 连调 `list_agents` 1220 次 | 烧光两次模型额度；插件的 guard 现在直接拒绝 |
| `bash echo "waiting"` | 什么也没等到，白花一次调用 |
| 空问题 `ask_user_question`（`options: []`） | **把流水线卡死**在一个用户无法回答的选择框上；guard 现在直接拒绝 |
| 问用户「继续等待还是中止？」（带两个像样的选项） | 把等待责任推给用户；一个 turn 里问了四次。**派出子代理后到做出实质工作之前，guard 拒绝一切提问** |

**「子代理跑得久」不是一个决策点，是正常情况。** 不要为此征询用户意见——他们没有让子代理更快完成的办法，而这条流水线承诺规格落盘后零打扰。真觉得它死了，就按上面「等不到有效结论」的三种处置办，那里没有一条是问用户。

看到自己正准备调用一个「占位」性质的工具，就是这一条被触发的信号：删掉那次调用，写上面那行交班记录。

**尤其不要用 `list_agents` 来等。** 它列的是子代理会话，不含任何结论内容。连续调用它是这份协议最常见、也最贵的失效模式：真实会话里编排者一次连调 149 次、单次会话累计 1069 次，把用户的模型额度烧光（403 usage limit）才停下——而期间子代理的回报早已到达，循环却没被打断。插件为此装了 guard，连续调用超过配额会被直接拒绝。

**不要拿子代理 id 去调 `job_output` / `job_list` / `job_kill`。** 那三个管的是 **shell 后台作业**（例如你自己用 `&` 起的服务），与子代理是两套东西，必然失败。查自己起的后台进程时它们是正常工具。

新一轮开始时，先数收到了几条结算通知。**没到齐就再结束一轮**，同样什么工具都不调。全部到齐才进入下面的分类。

### 等不到有效结论

**先确认你真的等过**：至少结束过一整轮、期间什么工具都没调，才算等过。同一轮里连查几次不算。

等过之后仍然没有通知，才用 `list_agents` **查一次**，按状态分三种处置：

- `running` —— **还在干活，继续等**。慢不等于失败。回到上面的做法：结束这一轮。
- `idle` 或 `ready`，但没有结算通知、或摘要里没有实质内容 —— 用 `send_message` 要一次：「把完整评审意见用 `write` 写到 `<你给它的路径>`，然后把摘要作为你的下一条消息发出来：文件路径、几条阻塞项、每条一句话」。
- 不在列表里 —— 按「某个 reviewer 子代理被中断」处理，**中止**。

**等不到就自己评审，是这份协议最严重的违规。**

## 常见误判

| 念头 | 现实 |
|---|---|
| "reviewer 工具调用有返回值了，说明它评审完了 / 没意见" | 返回值只是一条子代理 id 的回执；结论经结算通知另行送达，没到齐之前不能当作"没意见" |
| "用 `run_in_background: false` 让 reviewer 立刻把结果给我，省事" | 前台调用不会留下可复审的子代理 id，之后 `send_message` 复审就发不出去了 |
| "我在这一轮里多查几次状态，等它跑完" | 通知只能在**新的一轮**到达。同一轮里轮询永远等不到 |
| "我说了『停止轮询，等待通知』，然后再查一次确认" | 说要停不等于停。**结束这一轮 = 本次响应不调用任何工具**。说完又调工具就是没停 |
| "`list_agents` 只是查看，不算轮询" | 连续调用它就是轮询。插件的 guard 会在超过配额时直接拒绝 |
| "先跑个 `bash echo waiting` 占一下位，表示我在等" | 那不是等待，只是一次白花的调用。写交班记录那一行才是收尾 |
| "发个占位问题给用户，等 reviewer 回来再继续" | 空 `options` 的提问会把流水线卡死在用户无法回答的框上，guard 直接拒绝 |
| "每轮都被叫醒，那我每轮查一次状态总没错" | 有活跃 goal 在唤醒你。派出子代理后先 `update_goal` pause，否则每轮空转 |
| "子代理跑太久了，问问用户要不要继续等" | 那是把你的工作交给用户。等待期内 guard 拒绝一切提问；久不等于坏 |
| "这是个长任务，先 `create_goal` 立个目标" | 流水线自带事件驱动，goal 只会在等待期间反复叫醒你。不要创建 |
| "这条阻塞项就改一行，我直接改比派子代理快" | 你改的代码没经过任何评审。代码阻塞项一律派 implementer，不论多小 |
| "把阻塞项写进 `todo_write` 好跟踪进度" | 那是你自己的待办清单，写完就会照着自己做。要记就记成「派 implementer 修 Bx」 |
| "复审的意见让它追加到上一轮那个文件里" | 上一轮的文件是那一轮的证据。每轮各自成文，`_r<N+1>` |
| "复审只是确认一下，不用再落盘" | 那一轮的结论就此只存在于会话里，关掉就没了，报告也引用不到 |
| "用 `job_output` 把子代理的输出取出来" | `job_*` 管的是 shell 后台作业，不是子代理。子代理没有取输出的接口 |
| "收到 `reported:` 了，它评审完了" | `report` 可以中途调用。做完的判据只有结算通知那一行 |
| "通知说 `ran out of room` / `was stopped`，但内容看着挺完整，就用吧" | 那几种开场白明说它没做完，结论不可信。**中止** |
| "等了两轮还没通知，reviewer 大概挂了，我自己评审吧" | 先用 `list_agents` 看状态：`running` 就继续等。**自己评审等于没有评审** —— 宁可中止并报告 |
| "reviewer 只回了一句'评审完成'，我按它大概会说的处理" | 先核对它该写的那个评审文件在不在；不在就用 `send_message` 要一次 |
| "摘要说有 4 条阻塞项，我把评审文件整篇读进来看看" | 读细节是按需的。整篇读进来等于放弃了让它落盘省下的上下文 |
| "两个 reviewer 我给了同一个文件路径，反正内容会合并" | 后写的覆盖先写的，两份意见都没备份。一个 reviewer 一个文件 |
| "把改好的整份计划 `write` 出去，一次搞定" | 输出量等于文件全长，超过模型单次上限会被静默截断，那一轮以 max-tokens 结束且不会自动继续。先 `cp` 再逐处 `edit` |
| "四条阻塞项分四次 edit 太啰嗦，一次改完" | 一次响应改完四处的输出量是四段替换之和，正是撞上限的路径。一处一次 |

## 评审意见落盘

**reviewer 自己写文件，你只负责指定路径并核对。** 意见全文因此不必挤进「只有最后一条消息会被带回」那个通道，也不占你的上下文。

### 发起时：给每个 reviewer 一个专属路径

在 prompt 里给出它该写的文件的**完整路径**，一个 reviewer 一个文件：

```
docs/reviews/YYYY-MM-DD-<topic>-<spec|plan|code>_r<N>-<reviewer 工具名>.md
```

`<N>` 是本轮轮次。三个评审环节各自成文，同一环节的每一轮各自成文，同一轮的每个 reviewer 各自成文——路径撞车会让后写的覆盖先写的，而两份意见都没有备份。

reviews 目录路径以 `artifactDirs` 配置为准，`docs/reviews` 只是默认值。

### 收到通知后：先核对文件

结算通知里的摘要只说了「记了几条阻塞项」。**在分类之前，先确认文件真的存在**（`test -f <路径>` 或直接读它）。

- 文件在 —— 从摘要判断有没有阻塞项；需要细节时才读文件。**不要把全文读进来**，那等于放弃了让它落盘的全部好处。
- 文件不在，或者里面没有实质内容 —— 用 `send_message` 要一次：「把完整评审意见用 `write` 写到 `<路径>`，然后回一条摘要」。
- 再要一次仍然没有 —— 用你手上的摘要**自己**把这份文件写出来（写明「本文由编排者据 reviewer 摘要转录，reviewer 未自行落盘」），然后继续。一份没写下来的评审等于没评审，但也不值得为落盘失败中止整条流水线。

### 你自己要追加的一节

分类之后，在**每份**评审文件末尾追加一节，记你的判断：

- 哪些判为阻塞、哪些非阻塞（分类是你的判断，不是照抄 reviewer 的标签）
- **驳回的意见及理由**——这一节只能由你写，reviewer 不知道自己被驳回了
- 本轮是否收敛

**追加用 `edit`**，在文件末尾插入这一节；不要读出来再整份 `write` 回去（理由见下面「怎么改」）。这些文件是评审过程的唯一持久记录，最终报告只引用它们的路径。

## 分类

意见落盘之后，把问题分成两类：

**阻塞** —— 错误、自相矛盾、关键内容缺失、会让后续步骤失败或功能不正确。
**非阻塞** —— 风格、措辞、锦上添花、"覆盖率可以更高"。

分类是你的判断，不是照抄 reviewer 的严重性标签。**reviewer 可能是错的**：你有它没有的上下文。驳回一条意见时，把理由写进那条意见所在的评审文件 —— 被驳回的意见不计入阻塞，但必须留痕，让人能复核你的判断。

## 收敛判据

**全部 reviewer 都没有阻塞项** = 收敛，进入下一步。

有阻塞项且未达轮数上限 → 修复 → 复审 → 再判一次。

**修复由谁做**：规格与计划的阻塞项，你自己改；**代码的阻塞项，一律派 `subagent_implementer` 改**。理由是文档修改通常是局部改写，你本来就持有全部上下文；代码修复需要跑测试，那是 implementer 的职责。

### 代码阻塞项：一律派出，不论多小

**「这条只改一行，派子代理不值得」是错的判断。** 你直接改的代码没有经过任何评审——原作者的产出至少过了一轮 reviewer，你的补丁一次都没过。而且改代码要读文件、跑测试，那些内容会挤占你还要用来跑完剩余步骤的上下文。

一次派一个，每个 implementer 的 prompt 里必须给**两个**路径：

1. **计划文件路径**（收敛后的最终版本）——纪律 guard 校验的就是它，缺了这一项调用会被直接拒绝。评审文件在 reviews 目录、不在 plans 目录内，**只给评审文件路径过不了 guard**。
2. **评审文件路径，加上要修的那几条编号**——这才是告诉它改什么的依据。让它自己去读，不要把评审意见全文贴进 prompt。

再加一句「修完自己提交，不要 amend 或 rebase 已有提交」。

### 不要用 `todo_write` 记录阻塞项

`todo_write` 写的是**你自己**的待办清单。把「修复 B1: ...」写进去，等于向自己声明这件事由你做——真实会话里编排者刚说完「让我制定修复计划并派出实现子代理」，紧接着用 `todo_write` 列了 10 条「修复 Bx」，下一句就变成「让我开始修复阻塞项。先处理可以快速修复的问题」，然后自己 `git rm --cached` 清了一批文件、自己跑了 `tsc` 与 `uvicorn` 验证。它最终仍然把这 10 条派给了 implementer，但那一段自己动手的工作既没经过评审，也没有任何记录。

要跟踪进度就把条目写成分派动作（「派 implementer 修 B1」），或者干脆不用它——阻塞项清单已经在评审文件里，那份文件才是权威记录。

**修规格和计划时另存新版本，不要原地改。** 第 N 轮评审的对象是 `_rN`，修复后写成 `_r<N+1>`，旧版本原样留着。这样每一轮的输入输出都可追溯，复审者也能对比两版差异。代码不适用这条——代码的版本由 git 提交承担。

### 怎么改规格和计划：先复制，再逐处替换

（本节只针对你自己改的文档。代码由 implementer 改，见上。）

两步，顺序不能反：

1. **先用 `bash` 复制出新版本**：`cp docs/plans/<name>_r1.md docs/plans/<name>_r2.md`。复制不产生任何模型输出。
2. **再对新版本逐处 `edit`**，一个阻塞项一次调用，每次只给出要替换的那一段。

**不要用 `write` 重写整份文件。** `write` 的输出量等于文件全长，一份几百行的计划就是几万 token。模型有单次响应的输出上限（例如 `kimi-for-coding` 只有 32,768），超出会被**静默截断**：那一轮以 `max-tokens` 结束，你不会收到任何提示，不会自动继续，整条流水线就停在那里——看起来像卡死，实际是你的一次输出太长了。

**也不要试图在一次响应里改完所有阻塞项。** 一处一次 `edit`，改完一处再改下一处。四条阻塞项就是四次 `edit` 调用，那是正常的，不是低效。


**复审用 `send_message` 发给同一个 reviewer 子代理**，不要重新起一个。它保留着上一轮的上下文，复审只需读变更部分。不要重述已经通过的部分 —— 否则省 token 的说法就不成立了。

复审消息必须包含三样：

1. **新版本的路径**（`_r<N+1>`）与改了什么、哪几条待确认。
2. **这一轮它该写的新评审文件路径**——`..._r<N+1>-<reviewer 工具名>.md`。**每一轮各自成文，不要让它改上一轮那份**：上一轮的文件是那一轮的证据，被覆盖就没了。
3. 一句「结论仍然只放摘要，全文写进上面那个文件」。

**每一轮的评审意见都要落盘。** 真实会话里规格评审到了 r3、计划评审到了 r4，而 reviews 目录只有 `_r1` 的文件——第 2 轮之后的评审结论只存在于会话上下文里，会话一关就没了，最终报告也无从引用。收到复审的结算通知后，和首轮一样核对文件是否真的出现；没有就按上面「收到通知后：先核对文件」的三种处置办。

**修复后必须复审。** 自己改完自己说通过，等于没评审。

## 轮数上限

达到配置的上限仍有阻塞项 → **停止循环**，把剩余阻塞项写成遗留清单，继续下一步，并在最终报告里显著标注。

轮数上限是配置项（`pipeline.maxConvergenceRounds`），默认 3；部署方可以调整。你看不到当前实际配了多少，没被明确告知就按 3 处理。

不要因为"只差一点"再来一轮。上限是规格，不是建议。

## 记录

每一轮的完整记录落在 reviews 目录的那些文件里（每个 reviewer 一份，见上）。最终报告只需引用这些文件的路径，加上每轮的轮次与收敛结果——不要把评审意见全文再抄一遍进报告。

如果某一轮的 reviewer 是被串行调用的（不在同一条消息里），记一次「串行降级」。不影响结论，但要让人知道。
