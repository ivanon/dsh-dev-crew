# 评审收敛协议

被 `crew` 在三个评审环节调用：规格评审、计划评审、代码评审。三处共用同一套判据。

## 一轮的执行

**在同一条消息里同时调用全部 reviewer 工具。** 工具名是 `subagent_reviewer`（只有一个模型时）或 `subagent_reviewer_<alias>`（配了多个模型时），同一个角色只会是其中一种。用你自己的工具清单确认当前实际挂了哪些实例——`list_agents` 列的是已经存在的子代理会话，不是可调用的工具，这里用不上它。逐个串行调用不会让结论出错，但会白白拉长墙钟时间。

给每个 reviewer 的 prompt 里必须包含：

- **评审对象的文件路径**（规格/计划评审）或 **git 范围**（代码评审，形如 `<BASE>..HEAD`）。传路径，不传全文。
- 它自己去读的指令。评审者有文件读取工具。
- 判据：什么算阻塞、什么算非阻塞。

## 等结果

reviewer 工具走后台的 continuable 模式，`run_in_background` 省略时默认就是 `true`：调用立刻返回的是 `started subagent <id>`，**不是报告**。reviewer 的结论不会出现在这次工具调用的结果里。

**不要为了"马上拿到结果"把 `run_in_background` 显式设成 `false`。** 那会切到前台等待路径，前台调用不产生持久的子代理 id——复审要用的 `send_message` 从此没有对象可发。

### 结论怎么回来

子代理用 `report` 工具把结论送回给你。它到达时是**你的一条新消息**，形如：

```
Background subagent <id> reported:
<它的结论正文>
```

这条消息会**开启你的新一轮**。所以：

**发起全部 reviewer 之后，结束你这一轮。** 说一句「已发起 N 个 reviewer，等它们回报」然后停下。**不要在同一轮里等待、轮询或反复查状态** —— 报告不可能在你这一轮内到达，这一轮里你查多少次都只会看到「还在跑」。

**绝对不要用 `job_output` / `job_list` / `job_kill`。** 那三个是 **shell 后台作业**的工具，与子代理毫无关系；拿子代理 id 去调它们必然失败。子代理没有「取输出」的接口，结论只经 `report` 单向送达。

新一轮开始时，先数收到了几条 `Background subagent ... reported:`。**没到齐就再结束一轮**，同样不要轮询。全部到齐才进入下面的分类。

### 迟迟等不到回报

用 `list_agents` 看它的状态，按状态分三种处置：

- `running` —— **还在干活，继续等**。慢不等于失败。
- `idle` 或 `ready` 却没有回报 —— 它结束了却没调 `report`。用 `send_message` 要一次：「把你的评审结论用 `report` 工具发回来」。
- 不在列表里 —— 按「某个 reviewer 子代理被中断」处理，**中止**。

这是 `list_agents` 在这份协议里唯一该被用到的地方：判断子代理是死了还是仍在跑。它列的是子代理会话，不是报告内容，不能替代等待。

**等不到就自己评审，是这份协议最严重的违规。**

## 常见误判

| 念头 | 现实 |
|---|---|
| "reviewer 工具调用有返回值了，说明它评审完了 / 没意见" | 返回值只是一条子代理 id 的回执；结论经 `report` 另行送达，没到齐之前不能当作"没意见" |
| "用 `run_in_background: false` 让 reviewer 立刻把结果给我，省事" | 前台调用不会留下可复审的子代理 id，之后 `send_message` 复审就发不出去了 |
| "我在这一轮里多查几次状态，等它跑完" | 报告只能在**新的一轮**到达。同一轮里轮询永远等不到，只是白烧 token |
| "用 `job_output` 把子代理的输出取出来" | `job_*` 是 shell 后台作业的工具，与子代理无关。子代理没有取输出的接口 |
| "等了两轮还没回报，reviewer 大概挂了，我自己评审吧" | 先用 `list_agents` 看状态：`running` 就继续等。**自己评审等于没有评审** —— 宁可中止并报告「reviewer 未回报」 |
| "reviewer 已经评审完了，只是没发回来，我按它应该会说的处理" | 你没有它的结论。没收到就是没收到 |

## 分类

等全部完成通知到齐、拿到全部报告后，把问题分成两类：

**阻塞** —— 错误、自相矛盾、关键内容缺失、会让后续步骤失败或功能不正确。
**非阻塞** —— 风格、措辞、锦上添花、"覆盖率可以更高"。

分类是你的判断，不是照抄 reviewer 的严重性标签。**reviewer 可能是错的**：你有它没有的上下文。驳回一条意见时，把理由记下来 —— 被驳回的意见不计入阻塞，但必须出现在最终报告里，让人能复核你的判断。

## 收敛判据

**全部 reviewer 都没有阻塞项** = 收敛，进入下一步。

有阻塞项且未达轮数上限 → 修复 → 复审 → 再判一次。

**修复由谁做**：规格与计划的阻塞项，你自己改；代码的阻塞项，派 `subagent_implementer` 改。理由是文档修改通常是局部改写，你本来就持有全部上下文；代码修复需要跑测试，那是 implementer 的职责。

**复审用 `send_message` 发给同一个 reviewer 子代理**，不要重新起一个。它保留着上一轮的上下文，复审只需读变更部分。复审消息只写「改了什么」和「哪几条待确认」，不要重述已经通过的部分 —— 否则省 token 的说法就不成立了。

**修复后必须复审。** 自己改完自己说通过，等于没评审。

## 轮数上限

达到配置的上限仍有阻塞项 → **停止循环**，把剩余阻塞项写成遗留清单，继续下一步，并在最终报告里显著标注。

轮数上限是配置项（`pipeline.maxConvergenceRounds`），默认 3；部署方可以调整。你看不到当前实际配了多少，没被明确告知就按 3 处理。

不要因为"只差一点"再来一轮。上限是规格，不是建议。

## 记录

每一轮记下：调用了哪些 reviewer、各自提了几条、分类结果、驳回了哪些及理由、本轮是否收敛。这些进最终报告。

如果某一轮的 reviewer 是被串行调用的（不在同一条消息里），记一次「串行降级」。不影响结论，但要让人知道。
